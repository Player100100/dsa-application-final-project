# 实验记录：M1 仿真环境接通（ros2-masterX3）

- **日期**：2026-11-25
- **目的**：把课程发放的 Gazebo 仿真器接进本项目，验证 `/scan`、`/odom`、
  `/imu`、`/cmd_vel`、TF 和端到端导航
- **环境**：Windows 11 + VMware Workstation 25.0；OVF 导入为
  `ros2-masterX3`；NAT `192.168.150.131`；Ubuntu 22.04.5；ROS 2 Humble；
  Gazebo Fortress；VM 调到 **4 vCPU / 4 GB**（宿主机 15.7 GB，默认 8 GB 会拖垮宿主）
- **数据性质**：**仿真（Gazebo）**，不是 mock，也不是真车

## 1. 接入过程中修掉的三个问题

### 1.1 OVF 导入后开不了机：hardware version 99

`ovftool 5.0` 生成的 VMX 写的是 `virtualhw.version = "99"`，Workstation 25
启动时报：

```text
The virtual machine is using a hardware version that is not supported
by this version of VMware Workstation.
```

OVF 原始信息是 `vmx-21`，把 VMX 改成 `virtualhw.version = "21"` 后正常启动。

### 1.2 无界面启动时雷达全是 NaN

现象：`/scan` 有 1080 束、约 7.2 Hz，但 `ranges` 全是 `nan`；
`ScanMapper` 一束都写不进去，地图 100% 未知。

原因：SSH 启动的进程没有 `DISPLAY`，Gazebo 日志写
`Unable to open display: . Trying to run in headless mode.`；GPU 雷达拿不到渲染上下文。

修复：启动脚本里加

```bash
export DISPLAY=:0
export XAUTHORITY=$(ls /run/user/1000/.mutter-Xwaylandauth.* | head -1)
```

（本机是 Wayland + Xwayland :0，auth 文件名每次会话会变，所以用通配。）
修复后同一话题的 `ranges` 变为有限值（如 3.45 m），建图正常。

### 1.3 `get_transform` 报找不到 `yahboom_rosmaster_tf`

原因：rosbridge 是单独启动的，只 source 了 `/opt/ros/humble/setup.bash`，
**没有 source 工作空间** `~/Desktop/virtual_car/install/setup.bash`，
所以无法导入自定义 srv。修复后 `base_link ← laser_link` 返回
偏航 +3.1416 rad、位置 (0.043, 0)，与 SDK 文档一致。

## 2. 最终启动方式

```bash
# 仿真（headless，无 Gazebo GUI/RViz）
source /opt/ros/humble/setup.bash
source ~/Desktop/virtual_car/install/setup.bash
ros2 launch --noninteractive yahboom_rosmaster_bringup rosmaster_x3_sim.launch.py \
  gui:=false headless:=true rviz:=false use_camera:=false \
  enable_calculated_odometry:=false enable_ground_truth:=false \
  gazebo_use_llvmpipe:=true gazebo_model_detail:=box \
  gazebo_physics_step_size:=0.002 world:=maze_3_6x6.world \
  spawn_x:=0.0 spawn_y:=0.0 spawn_yaw:=0.0

# rosbridge（必须和上面一样 source 工作空间）
ros2 launch --noninteractive rosbridge_server rosbridge_websocket_launch.xml port:=9090
```

脚本已放在虚拟机 `~/sim_start.sh`、`~/bridge_start.sh`、`~/sim_ideal.sh`。

## 4. 导航结果

统一命令（仿真参数）：

```bash
python demo/nav_demo.py --ip 192.168.150.131 --goal <X> <Y> --duration 120 \
  --speed 0.15 --inflate 0.15 --stop-distance 0.18 \
  --cluster-slow-distance 0.30 --lookahead 0.30
```

| # | 配置 | 目标 (m) | 结果 | 用时 | 备注 |
|---|---|---|---:|---:|---|
| 1 | physical / stress | (1.5, 0) | 到达 | 6.9 s | **无效**：当时雷达 NaN，地图全未知，等于直线盲走 |
| 2 | physical / stress | (2, 2) | 到达 | 49.4 s | 明显抖动；地图 未知 61.6% / 占据 2.9% |
| 3 | physical / stress | (0, 2) | 超时 | >100 s | 停在 0.35 m；窄道 + 打滑，反复硬停转向 |
| 4 | ideal / ideal | (1.5, 0) | 到达 | **8.2 s** | 从原点直线，地图 未知 82.3% / 占据 1.5% |
| 5 | ideal / ideal | (2, 2) | 到达 | 49.8 s | 中段有约 37 s “无路径-探索”，之后恢复 |

结论：
- **链路和数据正确**：雷达、里程计、IMU、TF、速度指令全通；
- **控制还不够好**：窄道里 `front_range` 硬停与避障转向会互相打架，
  加上 `stress` 运动模型的打滑，出现来回摆头；
- **不是传感器问题**：ideal 配置也出现了“无路径”停顿，说明主要矛盾在
  建图/规划的膨胀带与恢复策略，而不是 `stress` 打滑；
- 两套运动模型（`motion_profile=ideal|stress`）和两套传感器模型
  （`sensor_profile=ideal|physical`）正好是天然的 Sim2Real 对照，
  下一轮应按同一目标点各跑 5 次填表。
