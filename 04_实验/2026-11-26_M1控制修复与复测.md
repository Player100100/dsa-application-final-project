## 3. 三个重要发现

### 3.1 (2,2) 在真实仿真世界里是墙

用保存的建图结果检查：**目标 (2,2) 在 live map 中为占据（100）**，
A* 报“终点不可达”；而 `maps/maps/maze_3_6x6.yaml` 同一位置是空闲（0）。

结论：**不要用 `maps/` 里的静态 YAML 选目标点**；它与 Gazebo 实际世界
在局部不一致（至少 (2,2) 处有墙）。目标点应以 live map 的空闲格为准，
或直接用 `(1.5,0)`、`(1,2)`、`(0,2)` 这组已验证可达点。

### 3.2 `/scan` 中继跑一段时间后会停

长时间运行后：`/internal/scan` 仍以 7.2 Hz 发布，但 `/scan` 没有数据；
`scan_qos_relay` 进程还在。重启仿真即恢复。直接订阅 `/internal/scan`
（`--scan-topic`）因 QoS 不匹配，拿不到数据。

对策：**每批实验前重启一次仿真栈**（`start_sim_stack.ps1`），不要一次
仿真连跑一整天；真车/课程最终版可能修掉这个问题。

### 3.3 `is_connected` 是 property

SDK `RobotClient.is_connected` 是 property，调用 `is_connected()` 会得到
`'bool' object is not callable`。已在 `robot_io` 修正；发送失败时先等 3 s
重连再重试一次。

## 4. 结论

- **ideal 路径已可用**：三个目标全部平稳到达，短目标 6.6–8.3 s；
- **stress 仍有真实差距**：同一个目标在打滑模型下卡在窄口，倒车能脱困但
  会回到同一状态，说明是“路径可通行但车体/控制过不去”，不是地图错；
- 这正好构成 Sim2Real 的对照素材：ideal 与 stress 的差异要写进报告，
  而不是把 stress 调成 ideal。

## 6. 追加：stress 参数扫描与真值里程计对照

### 6.1 参数扫描（目标 (1,2)，每次重启仿真）

| speed | lookahead | 结果 | 剩余距离 |
|---:|---:|---|---:|
| 0.10 | 0.30 | 超时 | 1.79 m |
| 0.10 | 0.40 | 超时 | 1.78 m |
| 0.15 | 0.30 | 超时 | 1.76 m |
| 0.15 | 0.40 | 超时 | 1.78 m |

四组都卡在同一位置附近 `(0.4, 0.34)`，即离起点约 0.5 m 的第一个窄口；
`vx` 反复在 0 / -0.08 / 0.10 之间切换，`near` 在 0.13–0.19 与 `inf` 间跳。

### 6.2 换 ground truth 里程计

用 `enable_ground_truth:=true` 启动仿真，`--odom-topic /ground_truth/odom`
（并加 `MSYS_NO_PATHCONV=1`，否则 Git Bash 会把 `/ground_truth/odom`
转成 `D:/Git/ground_truth/odom`）：

- 结果：**仍然卡在同一位置**，剩余 1.76 m。

结论：**不是轮式里程计打滑/漂移**。在真值位姿下同样过不去，说明问题在
“车体与窄口的几何/接触”层面：要么 gap 比车体窄，要么 stress 接触模型让
车在该处失去推进力。ideal 模型下同一目标能通过，进一步支持这一判断。

### 6.3 新增的调试开关（已保留）

- `--front-half-angle`：前向危险扇区半角，默认 0.35；窄道可试 0.22（本轮无效）；
- `--odom-topic`：换 `/ground_truth/odom` 做诊断；
- `--scan-topic`：理论可绕开 `/scan` 中继，但 `/internal/scan` 的 QoS 不匹配，
  实测拿不到数据；
- `--debug`：状态行额外打印 `error / near / hold`，本次定位就靠它。

### 6.4 对 Git Bash 的提醒

Git Bash（MSYS）会把以 `/` 开头的参数当路径转换：
`--odom-topic /ground_truth/odom` 实际传成 `D:/Git/ground_truth/odom`。
在 Bash 里跑时加 `MSYS_NO_PATHCONV=1`，或写成 `//ground_truth/odom`；
PowerShell 无此问题。

用 ideal 短目标那张 live map（388 个占据格）与
`maps/maps/maze_3_6x6.yaml` 做平移搜索（±1 m，0.05 m 步长）：

## 8. 追加：批量实验暴露的运行环境问题与修复

### 8.1 4 GB 内存不够，Gazebo 被 OOM

批量重启约 10 次后，虚拟机 3.8 GB 内存耗尽、swap 2 GB 全满，
Gazebo 被内核杀死（`exit code -9`），rosbridge 仍在但收不到任何话题数据。
把 VM 内存调到 **6 GB**（`memsize = "6144"`）后恢复。

### 8.2 重启残留进程与 FastDDS 共享内存

热重启时 `stop_sim.sh` 没杀干净 `parameter_bridge`、`ros2 launch` 等进程，
留下 FastDDS 共享内存/端口锁，日志出现：

```text
RTPS_TRANSPORT_SHM Error] Failed init_port fastrtps_port7411: open_and_lock_file failed
```

表现为 `/scan`、`/odom` 在 guest 里正常，但 rosbridge 订阅后收不到数据。
修复：
- `stop_sim.sh` 增加 `pkill -9` 覆盖 `parameter_bridge / ros_gz_bridge /
  controller_manager / spawner / imu_filter_magwick / ros2 launch`，
  并清理 `/dev/shm/fastrtps_*`、`/dev/shm/sem.*`、`/tmp/rosmaster_gazebo_*`；
- 所有脚本改用 **UDP-only FastDDS profile**（`~/vm/fastdds_udp.xml`，
  `FASTRTPS_DEFAULT_PROFILES_FILE`），绕开 SHM 端口冲突；
- 新增原子脚本 `~/vm/run_stack.sh`：stop → 确认无残留 → start → 重启 bridge，
  避免“旧仿真没死、新仿真没起、预检却通过”的竞态。

### 8.3 其他踩坑

- scp 上传的 `.sh` 带 CRLF，执行报 `/bin/bash^M: bad interpreter`；
  统一 `sed -i 's/\r$//'`，仓库里配 `.gitattributes` 更稳；
- 批量任务被停止时，子进程 `nav_demo.py` 会继续给车发速度，导致下一次
  仿真一启动车就在跑。停止批处理必须连子进程一起杀；
- `start_sim_stack` 现在会等到 `/scan` 与 `/odom` **真正有数据**才返回，
  不再只看 9090 端口。

### 8.4 世界选择：maze_3 太窄，改用 maze_1

- `maze_3_6x6`：ideal 与 stress 都卡在 `(0.4,0.34)` 的第一个窄口；
- `maze_1_6x5`：ideal (2,0) 12.4 s、stress (2,0) 12.2 s 均到达；
- 结论：不是算法/里程计，是 `maze_3_6x6` 的窄口宽度小于车体可通行宽度。
  基线改用 `maze_1_6x5`，`maze_3_6x6` 作为“窄道失败”对照保留。

### 8.5 真正的内存泄漏：孤立 rosapi_node

批量跑到约 10 轮后，VM 内存 5.1/5.9 GB、swap 1.4 GB。`ps` 显示十几个
**父进程为 1 的 `rosapi_node`**（每个约 80 MB）——`restart_bridge.sh`
只杀了 `rosbridge_websocket`，没杀它的伴生节点 `rosapi`，每轮重启漏一个。
另外还有重复的 `ign gazebo` / `ros2 launch`。

修复：`stop_sim.sh` 与 `restart_bridge.sh` 都增加 `pkill -9 -f rosapi`；
新增 `clean_all.sh` 一次性清理全部 ROS/Gazebo 残留；批处理每若干轮重启
一次虚拟机兜底。

### 8.6 补充：maze_1 静态图的一格偏移

用 5 张 maze_1 ideal live map 与 `maze_1_6x5.yaml` 比对：

- 原始重合率 60.7%（292–299 个占据格）；
- 平移搜索最佳为 **(dx=1, dy=1) 格 = (0.05, 0.05) m**；
- 校正后重合率 **85.4%**（85.3–85.6%），与 maze_3 的 85.3% 一致。

结论：课程提供的静态 YAML 与我们的 live map 存在**一格的原点/格子中心约定差**，
不是整张图错。做假墙统计必须先做这一格校正，否则会把 39% 的墙误判成“假墙”。
